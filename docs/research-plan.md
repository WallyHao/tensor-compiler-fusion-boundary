# Fusion Boundaries：TorchInductor 局部融合收益及其跨 GPU 预测

**项目定位**　编译原理课程研究与实践。RTX 3090 已完成源设备实验，RTX 4090 和 H800 PCIe 已完成目标设备验证。下一轮在自有 RTX 3090 上补采，检验更长的归约轴、输入布局变化和一个模型算子片段。[执行计划](../plan/README.md) · [数据归档与复核](../data/README.md)

## 研究对象与已有工作

考虑单消费者的生产者 → 消费者边。编译器可以物化中间张量并分别启动 kernel，也可以生成跨过这条边的 kernel。前者允许两段分别选择并行组织，后者有机会减少启动和中间读写。归约轴长度、输出行数和数据类型会改变这笔交易。课程实践要沿着同一条边展示从图、调度决策、生成代码到设备耗时的证据。

FusionStitching 已研究不同并行方式下的 GPU 融合，XLA GPU 的 PriorityFusion 已按估算的融合前后耗时差排序，并使用设备带宽。流式推理的区域级工作也已利用常规图和独立 kernel 的测量预测切分。我们的贡献定位为一次可复核的局部决策研究：在明确的编译产物和测量预算下，一个简单模型能预测多少收益，哪些决策仍然需要实测。[FusionStitching](https://arxiv.org/abs/2009.10924) · [OpenXLA 代价模型说明](https://github.com/openxla/xla/discussions/10065) · [流式推理切分研究](https://arxiv.org/abs/2610.35336)

## 研究问题与可检验预期

| 问题 | 检验 | 允许的结论 |
|---|---|---|
| RQ1 同一条合法切边在什么条件下值得消除？ | 固定模板、形状、类型、布局和后端，配对测量 split 与 fused，报告收益区间和默认决策 | 给出已测网格上的获益区、受损区、近似等价区和未判定区；有符号翻转才讨论边界所在的区间 |
| RQ2 启动、中间读写和调度资源能解释哪些现象？ | 比较普通启动与 CUDA Graph replay，检查生成代码，在预选子集对照显存计数器与资源分配 | 给出与机制一致或相冲突的证据。逻辑字节、实际显存流量和回归系数分别解释 |
| RQ3 编译两个候选后，只测 split，能否选出较快的版本？ | 在 3090 按整个算子模板留出，对比默认策略、恒选策略、字节阈值和代价模型 | 同时报覆盖率、决策准确率和错选增加的耗时。模型逊于默认策略也是可报告结果 |
| RQ4 预测能否迁移到另一张 GPU？ | 使用 RTX 3090 冻结的特征、系数和阈值，在 RTX 4090 与 H800 PCIe 上分别校准和采集 split，保存预测后再做配对计时 | 按设备、模式和共同配置报告覆盖与预测损失。三卡联合比较限于 H800 的 12 个已测配置 |

## 实验与模型

主后端为固定版本的 TorchInductor。TVM Relax 与 XLA 用于课程报告中的机制对照，比较合法性、候选生成和代价评估在各自流水线中的位置。Inductor 的完整调度包含依赖检查、重排和后端选择，一个配置阈值只能代表其中一部分。报告引用实测版本的源码位置。[TorchInductor 调度器](https://github.com/pytorch/pytorch/blob/main/torch/_inductor/scheduler.py) · [TVM Relax FuseOps](https://github.com/apache/tvm/blob/main/src/relax/transform/fuse_ops.cc) · [XLA PriorityFusion](https://github.com/openxla/xla/blob/main/xla/backends/gpu/transforms/priority_fusion.h)

第一阶段预注册两类逐元素模板和两类归约后处理模板，经过正确性、切边和实际执行验证后形成配对数据。设收益 B = T_split − T_fused，单位为微秒。主终点是稳态普通启动下每次调用的设备时间线跨度，CUDA Graph replay 用于对照启动开销。默认策略在相同编译配置下独立取证。图上重复使用同一中间值、生成器内联以及多阶段归约都需要从产物核实。[第一阶段任务入口](../plan/phase1-3090/README.md)

预测场景允许独立设备校准、编译两种候选并测量未融合基线。输入包括按设备校准的启动与逻辑传输时间，以及按编译元数据估计的资源变化。候选运行耗时和实测性能计数器仅用于评价或事后诊断。模型、缺失值处理、模板留出和指标在采集前约定；明确列出模型为决策付出的编译和测量代价。[分析与冻结协议](../plan/phase1-3090/05-analysis.md)

## 阶段、责任与交付

| 阶段 | 设备 | 已完成范围 | direct 标签（融合 / 等价 / 未定 / 拆分） | replay 标签（同序） |

| 源设备 | RTX 3090，Ampere | 72 配置，4,320 个有效配对 block | 68 / 3 / 1 / 0 | 25 / 33 / 14 / 0 |
| 迁移验证 | RTX 4090，Ada | 72 配置，4,320 个有效配对 block | 68 / 4 / 0 / 0 | 27 / 7 / 38 / 0 |
| 迁移验证 | H800 PCIe，Hopper | 预选 12 配置，720 个有效配对 block | 12 / 0 / 0 / 0 | 7 / 0 / 5 / 0 |

三卡均使用 PyTorch 2.6.0+cu124、Triton 3.2.0，驱动分别记录。H800 使用 Python 3.12.3，另两卡使用 3.12.15。两个目标设备的预测均在配对正式计时前冻结。direct 中，默认策略与两项、三项模型选对了所有明确标签。RTX 4090 的 replay 中，默认策略和两项模型各选对 27/27 个明确标签，三项模型选对 25/27。H800 的两种模式里，三种方法在已测子集上均选对所有明确标签。现有实验还没有给出明确的拆分占优样本。[归档与复算命令](../data/README.md#跨设备验证归档)

1. **RTX 3090 补采。** 预定 16 个新配置及 4 个原配置同期对照。优先检验长归约与非连续输入，再检验 RMSNorm 的逆 RMS 因子片段。主机执行者交付候选证据、配对数据、排除原因与复跑记录。[补采工作单](../plan/followup-3090/README.md)
2. **联合分析与课程报告。** 分别展示原网格、跨设备共同配置和 3090 补采的证据。比较默认策略与模型时注明覆盖率、明确标签分母和 regret。先在 3090 上复核任何新发现。当前采集安排使用自有主机，跨卡复测待本地结果出来后另行决定。

## 成功与失败的判据

课程成果以证据链验收。报告应能从原始行重建收益图，追溯决策到生成代码，说明适用范围，并量化选错的成本。找到收益翻转时，在同模板、布局和数据类型下给出相邻实测区间及复跑结果。若默认策略仍然接近最优，报告可优化的微秒数与补采覆盖范围。若归约配置无法配对，记录合法性、候选控制或计量的具体失败环节。跨卡预测退化时分别检查校准、候选结构变化和静态资源代理误差。
