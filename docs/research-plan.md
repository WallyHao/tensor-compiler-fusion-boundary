# Fusion Boundaries：TorchInductor 局部融合收益及其跨 GPU 预测

**项目定位**　编译原理课程研究与实践，三人协作。第一阶段完整实验在自有主机的 RTX 3090 上完成；当前仅安排这一款 GPU。跨架构迁移列为可选扩展，取得另一型号 GPU 后再确定验证设备。本文是研究设计，所有性能判断均待测量。

## 研究对象与已有工作

考虑单消费者的生产者 → 消费者边。编译器可以物化中间张量并分别启动 kernel，也可以生成跨过这条边的 kernel。前者允许两段分别选择并行组织，后者有机会减少启动和中间读写。归约轴长度、输出行数和数据类型会改变这笔交易。课程实践要沿着同一条边展示从图、调度决策、生成代码到设备耗时的证据。

FusionStitching 已研究不同并行方式下的 GPU 融合，XLA GPU 的 PriorityFusion 已按估算的融合前后耗时差排序，并使用设备带宽。流式推理的区域级工作也已利用常规图和独立 kernel 的测量预测切分。我们的贡献定位为一次可复核的局部决策研究：在明确的编译产物和测量预算下，一个简单模型能预测多少收益，哪些决策仍然需要实测。[FusionStitching](https://arxiv.org/abs/2009.10924) · [OpenXLA 代价模型说明](https://github.com/openxla/xla/discussions/10065) · [流式推理切分研究](https://arxiv.org/abs/2610.35336)

## 研究问题与可检验预期

| 问题 | 检验 | 允许的结论 |
|---|---|---|
| RQ1 同一条合法切边在什么条件下值得消除？ | 固定模板、形状、类型、布局和后端，配对测量 split 与 fused，报告收益区间和默认决策 | 给出已测网格上的获益区、受损区、近似等价区和未判定区；有符号翻转才讨论边界所在的区间 |
| RQ2 启动、中间读写和调度资源能解释哪些现象？ | 比较普通启动与 CUDA Graph replay，检查生成代码，在预选子集对照显存计数器与资源分配 | 给出与机制一致或相冲突的证据。逻辑字节、实际显存流量和回归系数分别解释 |
| RQ3 编译两个候选后，只测 split，能否选出较快的版本？ | 在 3090 按整个算子模板留出，对比默认策略、恒选策略、字节阈值和代价模型 | 同时报覆盖率、决策准确率和错选增加的耗时。模型逊于默认策略也是可报告结果 |
| RQ4 预测能否迁移到另一张 GPU？ | 冻结语料、特征、系数、阈值和分析规则，在另一型号 GPU 上重新测设备常数和 split，再解封 fused 标签 | 检验指定设备对上的迁移。跨卡差异涉及架构、缓存、带宽及调度等多种因素 |

## 实验与模型

主后端为固定版本的 TorchInductor。TVM Relax 与 XLA 用于课程报告中的机制对照，比较合法性、候选生成和代价评估在各自流水线中的位置。Inductor 的完整调度包含依赖检查、重排和后端选择，一个配置阈值只能代表其中一部分。报告引用实测版本的源码位置。[TorchInductor 调度器](https://github.com/pytorch/pytorch/blob/main/torch/_inductor/scheduler.py) · [TVM Relax FuseOps](https://github.com/apache/tvm/blob/main/src/relax/transform/fuse_ops.cc) · [XLA PriorityFusion](https://github.com/openxla/xla/blob/main/xla/backends/gpu/transforms/priority_fusion.h)

第一阶段预注册两类逐元素模板和两类归约后处理模板，经过正确性、切边和实际执行验证后形成配对数据。设收益 B = T_split − T_fused，单位为微秒。主终点是稳态普通启动下每次调用的设备时间线跨度；replay 是机制对照。默认策略在相同编译配置下独立取证。图上重复使用同一中间值、生成器内联以及多阶段归约都需要从产物核实。[第一阶段任务入口](../plan/phase1-3090/README.md)

预测场景允许独立设备校准、编译两种候选并测量未融合基线。输入包括按设备校准的启动与逻辑传输时间，以及按编译元数据估计的资源变化。候选运行耗时和实测性能计数器仅用于评价或事后诊断。模型、缺失值处理、模板留出和指标在采集前约定；明确列出模型为决策付出的编译和测量代价。[分析与冻结协议](../plan/phase1-3090/05-analysis.md)

## 阶段、责任与交付

1. **RTX 3090 单卡研究。** 在自有主机上重新编译候选并完成设备校准、试点和全量采集。编译负责人交付成对 IR、生成代码与默认路径。测量负责人交付校准、原始配对数据与质量记录。分析负责人交付可从原始记录重建的图表、错判案例和冻结包。第二人从清单复跑代表样本。这一阶段可以独立形成课程报告。
2. **可选的跨设备验证。** 使用冻结包，核对软件版本、候选结构和设备环境。分别报告同模板同形状的跨卡共同子集、仅在一张卡可实现的覆盖差异，以及逐模板预测损失。先保存预测再读取 fused 时间。若编译栈必须升级，另列软件版本影响，并在 3090 上用新版本复查共同代表点。
3. **扩展与写作。** 条件允许时用一个真实模型片段检查外部适用性。报告依次展示切边实例、方法和测量误差、单卡结果、可选的跨卡结果与失败案例。没有第二张卡的数据时，跨卡预测保持待验证状态。

## 成功与失败的判据

课程成果以证据链验收：能从原始行重建一张收益图、追溯一个决策到生成代码、说明适用范围，并量化选错的成本。性能提升、异号样本和硬件间翻转都是待检验的结果。若默认决策几乎总是正确，报告仍有多少微秒可优化；若有效样本仅覆盖逐元素类，明确归约失败发生在合法性、候选控制还是计量环节；若跨卡退化，分别检查校准、候选结构变化和静态资源代理的误差。全程保留未成对样本和排除原因，避免只展示成功融合。
