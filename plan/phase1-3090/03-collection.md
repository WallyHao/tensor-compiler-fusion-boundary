# C · 3090 正式采集协议

**输入**　通过核验的编译产物、环境清单与设备校准。计时对象是已编译的单图稳态调用。普通提交是主终点；对同一组产物再做手动 CUDA Graph replay，对照提交方式变化。两个模式分别存表和分析。

## 每个 case 的采集顺序

1. 用种子 17 的输入，预分配置于设备上的固定地址。编译、加载、调优与结果校验均在计时外完成。各策略使用相同输入内容、布局、stream、allocator 配置和输出生命周期；输入构造、拷贝、日志与 profiler 放在事件区间外。普通模式保留 wrapper 本身的正常工作。replay 每次重放包含一次完整调用的图，固定输入输出地址。
2. 每种策略预热至少 50 次并同步。先用短批估计每次时间，每个 case/mode 取同一个重复数 n，使更快策略的单批时间至少 5 ms；将 n 和试算值写入记录。批内连续调用，采用同一对 CUDA events 包围全批，在结束事件同步后读取 elapsed_ms。每次耗时为 elapsed_ms × 1000 / n。它包含设备在相邻提交之间等待的时间，描述连续调用条件下的吞吐摊销；单请求端到端延迟另行研究。
3. 用固定并记录的随机种子打乱 case 顺序。每个 case/mode 采 30 个配对 block。每块含 split 和 fused 各一批，15 块 SF、15 块 FS，顺序随机。每批前用该策略做同样的 5 次 untimed 调用并同步。两批相邻执行。两种模式的先后按 case 交替，记录实际顺序。每批落一条原始行并记录遥测时间窗。
4. default 若与某策略执行产物等价，记录证据并映射到该策略时间；若同分区生成了不同 kernel，单独测 default 作描述，其二选一决策仍映射到对应策略用于计算决策损失。第三种分区仅作描述。独立 default 计时使用相同预热、n 和 30 批，标明未配对。
5. 有污染、报错或缺一半的 block 全部保留，使用新 attempt 重跑整对，最多补两次；始终采用第一个完整且质量合格的 attempt。某模式未取齐 30 对则记录 incomplete，其他模式仍可独立完成。replay 捕获失败时保存错误；普通启动结果可进入主分析。
6. 对已通过的全部 72 个配置，理论上主策略共 72 × 2 模式 × 30 块 × 2 策略 = 8640 条有效批记录。实际按合法覆盖率对账，另列重试、校准、诊断和 default。逐批快照写暂存文件，再原子提交完成标记；恢复执行时检查已完成键和协议哈希。

## 机制诊断

固定预选 P1 最小/最大 N、R1 四个 (最小/最大 M, 最小/最大 K) 角点，均取 fp32。在普通模式计时结束后用独立进程逐 kernel 取 trace 或 Nsight Compute 计数器，记录工具版本、可用 metric 原名、单位、聚合区间与采样次数。关注 DRAM 读写字节、L2 流量、achieved occupancy、寄存器/线程、shared memory、spill 与 grid。字节按每次调用的 kernel 求和，占用率保留每 kernel 值。若无权限，从编译元数据提取静态资源量并标注来源；缺测写 null 和原因。每个合格点都报告普通与 replay 的配对收益，二者差值仅表示对提交方式的敏感性。

**复核**　由第二位执行者在正式数据归档后，用新进程、新 run_id 在同一 GPU UUID 上复跑两个试点和一个最大的合格 R2/fp16 点（先按 M 再按 K 排序）。引用原 run；报告区间、符号及差异。缺少对应模板时记明。正式 run 和复跑分别报告，保留相反结果。
