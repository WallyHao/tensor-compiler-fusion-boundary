# 03 · 审计与交付

## 复算和报告

1. 正式 `run.json` 核对 `expected_case_count=20`，`planned_template_counts={"R1":8,"R2":8,"N1":4}`，`expected_blocks=30`。三个工作组外的 `anchor` 四行也保留。用 `python -m fusionaudit build --run <正式目录> --out <独立分析目录> --strict` 生成审计，核对新模板入表。如果现有绘图未呈现跨布局匹配或 N1 图，从审计结果加补充图。复跑使用自己的实际清单计数和报告路径。
2. 每种模式列四组的计划数、可配对数、30 对齐全数与四类标签，另列无有效候选或缺测的原因。以 `B = T_split - T_fused` 为微秒收益，整对 bootstrap 10,000 次，默认 seed 2026，给出 95% 区间及 ±2% 四类标签，附 ±1%、±5% 敏感性。对照同 ID 的历史 3090 快照与同期 anchor，报告波动和运行环境差异。
3. 按 R1/R2 和 M 画固定布局下的 K 曲线。转置组与各自 `control_id` 并排给出 B 与区间。N1 独立汇报逆 RMS 因子片段的结果。明确拆分获益要求相对收益的 95% 区间完全低于 −2%。报告新发现是否在独立复跑重现。只有同模板、M、dtype、布局上的相邻 K 区间出现明确反向标签，才记录该区间内的符号翻转。
4. 默认映射到与明确标签相反的策略时，记录默认错选及额外耗时。若有冻结预测，用目标 `(case_id, mode)` 把预测与正式审计标签连接，逐组比较两项、三项、默认和恒选策略的覆盖率、明确标签准确率和 regret。现有 `compare` 子命令以源数据与目标数据的共同 ID 为分母，会漏掉 16 个新配置。补采评分采用正式有效的新配置与对照各自的分母，保留缺失预测。自动生成的本轮重拟合模型可作探索，冻结模型的汇报使用原 3090 系数及预先保存的预测。

## 归档与交接

- 在新的持久目录中整理配置清单及哈希、执行脚本、实际命令和 commit、环境、校准原始行、候选证据、试点、正式 timing 与失败行、诊断、复跑、冻结预测（如有）、审计结果与图表。打包时可排除可重建的编译缓存，核对正式 run 的 `SHA256SUMS` 覆盖的文件均在包内。
- 归档应同时有外部 SHA-256 和内部清单。解包后检查外部哈希、内部 `sha256sum -c SHA256SUMS`、严格审计和一个代表样本的 `fusionaudit trace`。记录 case ID、模式、原始行号、变体哈希和默认策略证据路径。
- 回传 commit 或分支、归档和校验和路径、一个追溯实例、四组各模式的计划/有效配置数、任何明确拆分收益或默认错选与其复跑结果。没有出现新现象时，交付已覆盖的配置范围和置信区间。保留排除的配置和失败原因。
